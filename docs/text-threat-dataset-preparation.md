# SecureSphere text threat dataset preparation specification

**Phase:** 1C planning only
**Research snapshot:** 2026-10-27
**Status:** No dataset is approved for collection, training, redistribution, or bundling by this document.

## 1. Executive summary and readiness

SecureSphere currently fails closed for valid `.txt` files. `textScanCore.ts` validates UTF-8 and rejects empty, malformed, and binary-looking content, then returns `UNSUPPORTED / TEXT_SCANNER_UNAVAILABLE` for otherwise valid text. `scanner.ts` routes text through that validator before the model-backed branch. `lgbmInference.ts` accepts a fixed-width numeric vector in a model-declared feature order; the bundled model loader and feature extractors are specific to PDF, Word, Excel, and HTML. There is no text model or text feature contract in the checked-in model set. These existing models cannot be treated as text classifiers by this plan.

| Category | Readiness verdict | Basis |
|---|---|---|
| Executable threats | **NOT SUITABLE YET** | The PowerShell candidate has no declared dataset license in the inspected card; Malicious Coding Intent has broad merged provenance and malware-code components with unresolved upstream rights; Atomic Red Team is an adversary-emulation test library rather than a labeled malicious-file corpus. New rights-cleared, context-rich samples and benign scripts are required. |
| Phishing and social engineering | **MORE EVIDENCE REQUIRED** | Several useful text collections exist, but task labels differ (spam, deception, smishing, phishing), real-message privacy and component rights need review, and two attractive sources have explicit or conflicting restrictions. Build a rights-cleared, context-rich phishing subset and representative benign set before model work. |
| Prompt injection | **MORE EVIDENCE REQUIRED** | Existing sources are mainly attack prompts or LLM benchmark contexts, not ordinary `.txt` documents; merged-source rights conflict or require gated/research use, and game success or unsafe-request labels are not equivalent to prompt-injection labels. Additional document-context annotation and source permissions are needed. |

These verdicts are dataset-readiness judgments, not findings that a model is ready. The candidates can guide a permission and annotation process; none is cleared here for any particular use. Public access, a repository-level code license, or a dataset-card license field is not sufficient by itself to establish rights over every row or over derived model weights. Hugging Face describes the license field as repository metadata; source materials still need review ([Hub license documentation](https://huggingface.co/docs/hub/en/repositories-licenses)). This is a documentary research record, not legal advice.

## 2. Existing project boundary

- `artifacts/securesphere/lib/scanning/textScanCore.ts` accepts UTF-8 validation only. Empty or invalid UTF-8 input is `CORRUPTED`, binary-looking text is `UNSUPPORTED`, valid text is `UNSUPPORTED / TEXT_SCANNER_UNAVAILABLE`; it never emits `SAFE`.
- `artifacts/securesphere/lib/scanning/scanner.ts` excludes `text` from `ModelBackedFileType`. It routes bytes to the text validator and clears the local byte buffer after that step. The model loader has explicit PDF, Word, Excel, and HTML cases.
- `artifacts/securesphere/lib/scanning/lgbmInference.ts` traverses the provided LightGBM tree JSON and checks that a feature vector has exactly `num_features`; `buildFeatureVector` uses `model.feature_names` order. Matching vector dimensions alone do not establish feature compatibility or training-domain compatibility.
- The visible bundled assets are `pdf.json`, `word.json`, `excel.json`, and `html.json`. The tracked training code/features are file-format-specific. Do not reuse those features or models for free text.
- Plaintext analysis remains on device. No future dataset workflow may send SecureSphere users' documents, extracted text, keys, or search tokens to a dataset host or training service. Dataset staging, if separately authorized, must use rights-screened research samples and access-controlled storage.
- Upload authorization remains SAFE-only. `UNSUPPORTED`, an uncertain/low-confidence classification, a missing or incompatible model, and an inference failure remain distinct non-SAFE outcomes.

## 4. Composition plan and hard negatives

Build three independent binary/uncertain targets; do not collapse them into a single “security-related” label. The same item may have more than one positive label, but each label must be justified separately. Keep source and context strata, languages, and document types visible in reports. Most candidates are English or code/prompt snippets; claims about other languages require their own rights-cleared samples and evaluation.

| Category | Positive evidence to include | Representative benign and hard negatives | Ambiguous/context examples |
|---|---|---|---|
| Executable threats | Harmful commands or scripts supported by contextual evidence of destructive, credential theft, persistence, exfiltration, unauthorized access, or payload execution intent. Use safely sourced static samples; never execute corpus items. | Routine administration, deployment, backup, endpoint management, installation scripts, logging, security configuration, authorized red-team/Atomic tests, and educational code examples. Security-related APIs/commands alone are not positive evidence. | Incident response writeups quoting commands; malware analysis reports; tutorials showing deobfuscation; code comments quoting payloads; scripts whose authorization/purpose is missing. Preserve surrounding document and mark uncertain where intent cannot be resolved. |
| Phishing/social engineering | Messages with observable deceptive request or impersonation intended to obtain credentials/secrets, induce money transfer, or reveal sensitive information; include channel and context. | Legitimate password resets, account notices, invoices, delivery alerts, payment reminders, marketing, urgent but authentic requests, internal security notices, and phishing-awareness training. Generic spam is its own attribute and is not automatically phishing. | Reported messages, quotes, simulations, forwarded chains, suspicious but context-free alerts, and false positive reports. Preserve sender/context only when rights/privacy permit; otherwise use redacted and documented examples. |
| Prompt injection | Text in an AI-consumed context that attempts to override or supersede system/developer/user instructions, disclose protected data, or misuse tools; record whether attack is direct or indirect and its intended target. | Normal instructions, task requirements, quoted attack strings in documentation, prompt-injection research, safety policies, benign role prompts, and documents with imperative/adversarial-sounding text that do not target an AI system. | Attack examples in threat reports, benchmark strings without surrounding context, user prompts with conflicting but non-malicious instructions, and untrusted quoted content. Label only with context and target behavior evidence. |

Do not generate harmful payloads merely to inflate counts. Security-test examples must be static, controlled, sourced with permission, and safely stored. For class balancing during model training, sample or weight training data only; never rebalance the locked test set to mimic deployment performance. Preserve a naturalistic test stratum and report results separately for source, language, context type, and hard negatives.

## 5. Annotation schema and review protocol

Each record is one text item with enough permitted surrounding context to interpret intent. Store raw content only in an approved, access-controlled corpus if collection is separately authorized. Do not include SecureSphere user documents. For research exports and reports, use stable IDs and redacted evidence references rather than exposing personal content.

| Field | Definition |
|---|---|
| `record_id` | Stable random UUID assigned by the project; not derived from text or personal identity. |
| `source_id`, `source_record_id` | Publisher and original row/document identifier; preserve original reference where terms allow. |
| `source_revision`, `retrieved_at`, `content_sha256` | Immutable commit/release/DOI version, acquisition date, and exact-byte hash. Never treat hash alone as rights clearance. |
| `source_license_claim`, `rights_status`, `rights_evidence_ref` | Publisher's exact license claim; project status `unreviewed`, `source_questions_open`, `qualified_review_pending`, `approved_scope_limited`, or `excluded`; link to permission/notice evidence. `approved_scope_limited` must name allowed use and expiry. |
| `labels.executable`, `labels.social_engineering`, `labels.prompt_injection` | Independent enum for each: `positive`, `negative`, or `uncertain`. Never infer one category's label from another. |
| `evidence_ref`, `rationale_code`, `context_ref` | Short label rationale and pointer/offset to permitted evidence and surrounding context. Keep exact quotations to the minimum needed and respect source terms/privacy. |
| `context_type`, `language`, `locale` | E.g. script, email/SMS, ordinary prose, documentation, benchmark prompt, quoted/security education; ISO language tag and known locale or `unknown`. |
| `annotator_id`, `annotated_at`, `review_status`, `adjudication_ref` | Pseudonymous reviewer, timestamp, review state, second-reviewer outcome and adjudicator reference. Do not put reviewer personal details in model data. |
| `exact_duplicate_group`, `near_duplicate_group`, `source_family`, `campaign_or_template_group`, `split` | Group IDs for content and provenance relations; `split` is assigned only after grouping and restricted to `train`, `validation`, `locked_test`, or `excluded`. |
| `privacy_status`, `redaction_status`, `retention_class` | PII/secret review, redaction action, and retention/access policy; values must be defined before acquisition. |

**Review rule:** use two independent annotators for each category, followed by adjudication for disagreements. `uncertain` is not a negative class: unresolved records are excluded from supervised fitting and primary metric denominators, then retained in a separate abstention/qualitative evaluation set if rights permit. Annotators must see enough context to judge whether code is authorized, a message is authentic, or an instruction is aimed at an AI system. Keep evidence-based labels distinct from automated model outputs.

## 6. Deduplication, grouping, and split rules

1. Before normalization, hash exact source bytes (SHA-256). Preserve source identity, source revision and license metadata beside the hash.
2. Normalize text with a versioned, category-aware pipeline: Unicode normalization, consistent line endings, and whitespace normalization for a second hash. Do not strip commands, URLs, identifiers, code syntax, or prompt delimiters that may carry threat evidence. Keep raw and normalized hashes separate.
3. Detect near-duplicates using conservative similarity methods appropriate to each category: AST/canonical command groups for scripts; normalized message/template/campaign and sender/campaign family for messages; attack-family, augmentation ancestry, benchmark/task/context family for prompts. Every transformation and threshold is versioned; candidates are manually reviewed. Avoid merging independent examples merely because they share common boilerplate.
4. If exact duplicates conflict in labels, hold the whole group for adjudication; if unresolved, exclude from supervised splits. Do not let one class label silently overwrite another.
5. Assign all duplicate and related-source groups to exactly one of train, validation, or locked test. Do not use random row-level splitting alone: repeated campaign messages, script variants and generated prompt variants leak nearly identical patterns across splits and overstate generalization.
6. Create the locked test set once, record its manifest hash and access controls, and do not inspect it for feature, model, or threshold selection. Use validation only for calibration and threshold choices.
7. In addition to a group-stratified split, reserve source-held-out evaluation wherever multiple independent sources exist. For social engineering, report a temporal holdout if dates are credible. For code, hold out script families/source repositories. For prompt injection, hold out source and attack-family groups. Report both in-domain and held-out results.
8. If a candidate's published random split cannot be mapped to groups, recompute a group split from authorized raw records; do not combine its pre-split partitions as if independent. Keep all test records locked.

## 7. Evaluation and deployment acceptance plan

Evaluate each category independently against adjudicated labels. Report sample counts and confusion matrices with counts (TP, FP, TN, FN), not percentages alone. Report precision, recall, false-positive rate `FP/(FP+TN)`, false-negative rate `FN/(FN+TP)`, and precision-recall AUC where meaningful. Provide confidence intervals overall and for each source, language, context type, and designated hard-negative group. Use exact binomial intervals for FPR/FNR and group-aware bootstrap intervals as a sensitivity analysis when samples are clustered. Calibration must be assessed on validation data; choose thresholds on validation only. Freeze model, preprocessing, and thresholds before opening the locked test.

**Provisional gates only (not measured):** at least 90% recall per category and a 95% confidence-interval upper bound for FPR below 0.1%, plus acceptable results on each prespecified benign hard-negative slice. These are project targets, not safety guarantees. A zero-false-positive observation needs roughly 3,000 independent benign test examples for a one-sided 95% upper bound around 0.1% (rule-of-three approximation). Correlation among templates, senders, scripts or prompts lowers the effective sample size; report independent group counts and use conservative intervals. If test data are too small to resolve the target, report the interval and mark the criterion unverified rather than claiming it passed.

Report per-category performance separately; a high aggregate score cannot hide weak results in one threat category. Include benign ordinary documents as a predeclared representative sample, not just constructed hard negatives. Report class/source/language prevalence and precision at the observed prevalence; a balanced research dataset does not establish real-world predictive value. Investigate false positives and false negatives with blinded reviewers and retain a reason-coded error log without sensitive raw content in general logs.

Before setting an on-device size/latency target, measure supported low-end devices and define maximum file size, memory and latency from product constraints. No numerical deployment budget is established by current project evidence; a target must be agreed and profiled before model selection. Text length, line count or formatting alone must not constitute threat evidence. If the target cannot be met with validated performance, keep text scanning unsupported.

**Outcome mapping:** only an in-scope, successfully processed input with a validated calibrated negative result may be considered for `SAFE`; a positive result is potential threat and blocked. Invalid encoding/content may be `CORRUPTED` only when an integrity/format check supports that finding. Out-of-scope language/context/size is `UNSUPPORTED`. Low confidence, unresolved label semantics, model/version mismatch, missing model and inference failure remain distinct uncertain/unsupported/error outcomes and never become SAFE. The three independent category outputs should be retained internally for transparent reason reporting; user-facing results must avoid claiming “safe” beyond the checks performed.

### 15.3 Overlap and duplication controls

- **PowerShell:** Fa2y explicitly references MPSD/Fang and should be treated as overlapping, not independent. Revoke-Obfuscation is a different corpus but its target label is obfuscation, not maliciousness. Before any future comparison, deduplicate script hashes and normalized/token/AST near-duplicates, keep source family and malware campaign together, and maintain a separate hard-negative set of legitimate administrative, educational, security-test and quoted scripts.
- **Phishing:** MeAJOR, Champa’s collection, the 2025 merged corpus, and AURA inherit or repackage overlapping legacy sources (Nazario, TREC, Ling, Enron, Nigerian Fraud, CEAS and SpamAssassin). No row-level crosswalk is available from the reviewed summaries. Exact/near duplicate checks must span all aggregates and upstream sources; identical messages, thread variants, forwarding chains, templates and campaign families must remain in one split. Historical time period and spam/scam labels must be retained as metadata rather than relabeled as contemporary phishing without review.
- **Prompt injection:** no evidence establishes row-level duplicate overlap among Boundary Pairs, NVIDIA, InjecAgent and AgentDojo. Their synthetic attacks may share familiar templates or model-generated conventions, and the benchmarks share broad attack concepts. Before combining, hash exact text and compare normalized/semantic near-duplicates; group by paired example, scenario, attack family, source generator/model and original task. Keep attack/benign pairs and all paraphrases in one partition. Benchmark task outcomes must not be mixed as if they were the same annotation target.

### 15.4 Ranked investigation shortlists and feasibility

**Executable threats**

1. **Priority 1 — MPSD:** closest new labelled script corpus and feature rationale. Required first: explicit data license/permission, pinned source version, complete source lineage, class/label rubric, dedup/split groups and rights for commercial model weights.
2. **Priority 2 — Malicious Coding Intent v6:** already in Phase 1D, still potentially richer labels but merged upstream rights and data-vs-code license scope are unresolved. Require row-level manifests and third-party grants before considering preparation.
3. **Fallback — Fa2y:** positive-only and overlaps MPSD; only source investigation, not independent training evidence.
4. **Reject for label use — Revoke-Obfuscation:** the project itself warns its labels are not malicious-intent labels.

**Feasibility:** no candidate currently supplies a defensible, rights-cleared set of malicious executable behavior plus representative benign administrative/security-test/documentation negatives. A credible path needs owner-cleared script sources and expert labeling by behavior and context, with inert and safe-to-handle samples. It cannot be generalized from PowerShell code to every plain-text file without separate evaluation.

**Phishing/social engineering**

1. **Priority 1 — MeAJOR:** explicit phishing/benign schema and multiple sources make it worth an owner-level lineage and rights inquiry; license field blank and counts/source permissions unresolved.
2. **Priority 2 — FERB:** synthetic, context-rich, privacy-conscious email source with published binary labels; rights are blank and municipal/generator narrowness limits generalization.
3. **Fallback — E-PhishLLM and PhishVN:** synthetic positives and benign examples may help fill multilingual/hard-negative gaps after pinned release, language/count correction, evaluation and rights confirmation. PhishVN’s synthetic message files and crawled-page data are distinct modalities and should not be conflated.
4. **Reject as independent/ground truth — AURA mirror and 2025 nine-corpus merge:** duplicated upstream corpora, unverified component permissions, and broad spam/scam labels.

**Feasibility:** a promising route exists if MeAJOR’s source rights can be cleared row by row and combined with permissioned, current, diverse benign customer-service/transactional/marketing messages and expert-labeled phishing/social-engineering examples. Without that, synthetic sources alone are not enough to claim real-world generalization. Unsolicited mail and scams are not synonymous with credential theft, payment fraud or coercion; preserve separate subtype labels and uncertain cases.

**Prompt injection**

1. **Priority 1 — Agentic Prompt-Injection Boundary Pairs:** explicit matched hard negatives, context fields, scenario groups and publisher-declared dataset CC BY 4.0 make it the strongest classification-oriented candidate for further permission and label audit.
2. **Priority 2 — NVIDIA Nemotron v1:** strong contextual indirect-injection and deterministic attack-success outcome, declared CC BY 4.0; single displayed train split and simulator-specific success limit its role.
3. **Fallback — AgentDojo and InjecAgent:** potentially useful locked external benchmark/context sources after rights are pinned; agent success outcomes are not text-only labels.
4. **Reject as ground truth — deepset `prompt-injections`:** label target is too broad/noisy as documented; aggregate Apache metadata does not resolve record provenance.

**Feasibility:** a pilot dataset is plausible for a narrowly scoped “instruction-boundary violation in AI-consumed content” label, but no source alone supports a general .txt maliciousness verdict. Add benign documents that discuss attacks, quoted/promotional instructions, policy documentation, code comments, prompt-engineering tutorials, security tests, and benign imperatives; annotate whether the text is an instruction to the model, a quotation/example, or ordinary content and whether it crosses a defined boundary. The target use case must define whether a standalone `.txt` is even consumed by an AI/agent; absent that context, the label can be intrinsically ambiguous.

### 15.5 Required hard negatives, annotation and split rules

For all three categories, retain positive, negative and uncertain values **per category**, not one mutually exclusive “safe/malicious” target. Store source ID/version and row locator; original-source provenance and rights status; language and collection/generation period; context type (`ordinary_document`, `quoted_attack`, `documentation`, `script`, `security_test`, `email`, `SMS`, `agent_tool_output`, etc.); label evidence and rationale; annotator/reviewer identifiers or role; ambiguity reason; and split group. Do not store private identities in the research export. Quoted threat material should be labeled by its communicative function and surrounding context rather than keyword presence.

- **Executable:** positives require evidence of harmful behavior or malicious intent in the script context; negatives must include normal administration, deployment/maintenance scripts, educational/tutorial examples, security tooling and authorized red-team tests. Treat obfuscation and dangerous-looking primitives as attributes, not labels by themselves.
- **Phishing:** positives require an evidenced deceptive request or lure (credential disclosure, payment/transfer, sensitive-data disclosure, or impersonation); negatives include normal account alerts, MFA/reset notices, legitimate invoices, marketing, fundraising, urgency without deception, and quoted phishing-awareness examples. Add uncertain labels for missing headers/context and spam-only labels.
- **Prompt injection:** positives require an instruction directed at an AI/agent that attempts to override its governing instructions, disclose protected information or misuse a tool; negatives include quoted/reported attacks, documentation, educational examples, policy text, ordinary imperative language and authorized security tests. Preserve whether the example was direct, indirect, context-embedded, or observed successful in a specific agent.

Use source, campaign, thread, conversation, script family, generation scenario, pair and paraphrase groups as indivisible split units. Normalize for exact duplicate detection, then run near-duplicate review (e.g. token/character shingles and semantic similarity) across all sources before splitting. Keep all near-duplicate clusters and transformed variants in one partition; reserve a source- or time-held-out final test set, lock it before threshold tuning, and never choose threshold from it. If too few independent groups exist for a stable estimate, report confidence intervals and state that the test set cannot support a reliable false-positive/false-negative claim.
